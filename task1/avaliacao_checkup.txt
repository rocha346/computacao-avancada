CRÍTICO 1. n = 14 na L1 do A64FX "cai no critical stride"        -> ERRADO
--------------------------------------------------------------------------
A conta está certa, a conclusão não.
  - Certo: n+2 = 16, cada array tem 16^3 x 4 B = 16 KiB; a L1d do A64FX tem
    64 KiB, 4 vias, linha de 256 B -> 64 conjuntos (sets); uma "via" inteira
    = 64 x 256 B = 16 KiB.
  - Errado: isso NÃO dá conflitos severos. Um array contíguo de 16 KiB passa
    exatamente UMA vez por cada um dos 64 sets. Os 3 arrays (u, u_new,
    material) põem 3 linhas em cada set, e cada set tem 4 vias. Cabe tudo,
    com 1 via livre em todos os sets (é por isso que 48 KiB cabem em 64).
    O "aliasing" só faz mal quando há MAIS endereços a cair no mesmo set do
    que vias (ex.: 5+ arrays com stride potência de 2, ou n+2 = 512 na RAM,
    onde muitos planos caem nos mesmos sets).
  - Os vizinhos i±1 estão a 1 plano = 16x16x4 B = 1 KiB de distância: caem
    em sets DIFERENTES (1 KiB / 256 B = 4 sets ao lado), não competem.
  - Detalhe real: no código do professor (varcoef/grid.cpp) os 3 arrays são
    malloc separados, não alinhados a 256 B. Então cada array ocupa 65 linhas
    e UM dos 64 sets pode receber 2 linhas de cada array (6 > 4 vias). Isso
    afeta ~1/64 das linhas: desprezável.
  - n = 13 não traz vantagem: com 13.2 KiB por array a distribuição é menos
    uniforme, não mais.
Opinião: manter n = 14. Se quisermos, a meia frase do relatório pode até
virar argumento a favor: "with n+2 = 16 each array is exactly one 16 KiB
way, so the three arrays fill 3 of the 4 ways evenly".

    nenhuma divisão. Mas a E2 ainda tem 1 divisão final, e o próprio texto

    tetos no artigo depende da máquina e do código. Meia frase, opcional.
