[D07] Latência da memória: pointer chasing próprio em C   (20/11/2026, Task 1.1)
Decisão:      Escrevemos um pequeno programa em C que percorre uma lista

Porquê:       - Cada load depende do anterior, por isso o processador não

[D08] Tetos (ceilings) da 1.3 para o box27              (20/11/2026, Task 1.3)
Decisão:      4 tetos de computação + 4 de memória, ordenados como no artigo
              (Williams et al. 2008): do mais provável de o compilador/código
              simples atingir (mais baixo) ao que exige mais esforço.
              Computação (de baixo para cima):
                C1. 1 thread, escalar (sem SIMD)   <- código de referência
                C2. todos os cores, escalar        <- paralelizar (OpenMP)
                C3. todos os cores, SIMD, sem FMA  <- vetorizar; teto realista
                C4. pico: SIMD + FMA               <- inatingível no box27
              Memória (de baixo para cima):
                M1. NUMA errado (first-touch num só socket/CMG)
                M2. sem cache blocking (u lido ~3x da RAM)
                M3. com write-allocate (stores normais)
                M4. STREAM medido (banda real)
Porquê:       - Cada teto corresponde a uma otimização concreta da Task 2, o
                que liga o roofline ao trabalho de otimização.
              - C3 é o teto realista porque o box27 tem ~26 somas e só ~4
                multiplicações por ponto: quase nada para fundir numa FMA.
              - Perder SIMD custa 8x no AMD (AVX2, 8 floats) e 16x no A64FX
                (SVE 512, 16 floats): o A64FX é mais sensível à vetorização.
              - M1: D04 (nó inteiro) torna a colocação NUMA crítica (2 sockets
                no AMD, 4 CMG no A64FX).
              - M2: 3 planos de u (~3 MiB para n=512) não cabem na L2 do AMD.
Alternativas: Só os tetos clássicos do artigo: menos específicos do box27.
Impacto:      Tetos C1-C4 medidos com o microbenchmark (D05); M1/M4 medidos
              com STREAM (D06); M2/M3 calculados a partir do tráfego.
Estado:       SUBSTITUÍDO por D16 (tetos refeitos para o varcoef).

[D09] Tamanhos da 1.4: por máquina em L1/LLC, igual na RAM (20/11/2026, Task 1.4)
Decisão:      Tamanhos (grelha n³ interior, referência box27 = 16 B/ponto com
              halo, (n+2)³ pontos):
                L1   AMD 7742 (L1d 32 KiB)  -> n = 10  (12³ x 16 B = 27 KiB)
                     A64FX    (L1d 64 KiB)  -> n = 13  (15³ x 16 B = 53 KiB)
                LLC  AMD (L3 16 MiB por CCX)  -> PROPOSTA n = 78 (~7.8 MiB)
                     A64FX (L2 8 MiB por CMG) -> PROPOSTA n = 62 (4.0 MiB)
                     (~metade da LLC vista por 1 thread: acima da L1/L2
                     privadas, com margem para conflitos e outros dados)
                RAM  igual nas duas -> PROPOSTA n = 512 (~2 GiB > 1 GiB;
                     cabe nos 8 GiB de HBM de 1 CMG do A64FX)
Porquê:       - O objetivo de cada tamanho é ISOLAR um nível da memória; as
                caches das duas máquinas têm tamanhos diferentes, logo o mesmo
                tamanho não isolaria o mesmo nível nas duas.
              - Na RAM o nível é "fora do chip" nas duas, por isso usar o mesmo
                tamanho permite comparar diretamente DDR4 vs HBM2.
              - Margem abaixo do tamanho da cache: há outros dados (pilha,
                código, halo), e associatividade limitada causa conflitos.
Alternativas: O mesmo tamanho em tudo: o tamanho "L1" de uma máquina não cabe
              na L1 da outra. Rejeitado.
Impacto:      Gerar com tools/gen_input.py box27 --dims n n n. Confirmar os
              tamanhos LLC com a curva de latência (D07). Se mudarmos as
              estruturas de dados (ex.: SoA, 12 B/ponto), recalcular.
              Discutir: n = 512 é potência de 2 -> possíveis conflitos de
              cache (aliasing); alternativa n = 500.
Estado:       SUBSTITUÍDO por D15 (valores para o varcoef). O princípio "por
              máquina em L1/LLC, igual na RAM" mantém-se.

[D10] Estatística: 10 repetições, mediana + IQR          (20/11/2026, Task 1.4)
Decisão:      Cada teste corre 1 vez de aquecimento (descartada) + 10
              repetições medidas. Reportamos a MEDIANA e o intervalo
              interquartil (IQR = Q3 - Q1); nos gráficos, barras de erro Q1-Q3.
Porquê:       - Os tempos de execução não seguem uma normal: têm cauda de
                outliers (ruído do SO, interrupções, variação de frequência,
                vizinhos na rede). A mediana não é puxada por esses outliers;
                a média é.
              - O IQR mostra a variabilidade (estabilidade da medição), o que
                alimenta o pensamento crítico ("o resultado é fiável?").
              - O aquecimento elimina efeitos de arranque (page faults na 1ª
                escrita, caches frias, frequência a subir).
              - 10 repetições: compromisso entre custo de horas no Deucalion
                e quartis estáveis.
Alternativas: 5 reps + média/desvio padrão (sensível a outliers);
              k-best (esconde a variabilidade).
Impacto:      Scripts de teste fazem 11 execuções por configuração e guardam
              todas as linhas CSV; o tratamento estatístico é feito depois.
              Se o IQR for grande (> ~5% da mediana), investigar a causa.
Estado:       DECIDIDO (Rodrigo, 20/11/2026)

Decisão:      - Base comum nos 2 CPUs: perf (contadores de hardware: ciclos,

[D14] Frequência do pico AMD: base 2.25 GHz + medida sob carga (20/11/2026, Task 1.1/1.2)

              (scaling_cur_freq até 3.4 GHz), acima da base de 2.25 GHz.

              com perf) e o roofline mostra as duas linhas.

Alternativas: Só base; só boost máximo. Rejeitadas pelas razões acima.
Impacto:      Fazer o mesmo no A64FX (frequência não visível no Linux) e na
              A100 (clock por defeito 1095 MHz vs máximo 1410 MHz).

[D15] Tamanhos da 1.4 para o varcoef                     (20/11/2026, Task 1.4)
Decisão:      Referência varcoef = 12 B/ponto (u 4 + u_new 4 + material int 4),
              (n+2)³ pontos com halo:
                L1   AMD 7742 (L1d 32 KiB)        n = 11  (13³ x 12 B = 25.7 KiB)
                     A64FX    (L1d 64 KiB)        n = 14  (16³ x 12 B = 48 KiB)
                LLC  AMD (L3 16 MiB por CCX)      n = 86  (7.8 MiB)
                     A64FX (L2 8 MiB por CMG)     n = 68  (3.9 MiB)
                RAM  igual nas duas               n = 500 (1.41 GiB > 1 GiB)
Porquê:       - Mantém o princípio de D09: isolar cada nível em cada máquina.
              - L1 A64FX: n = 15 daria 57.6 KiB em 64 KiB com associatividade
                4-way, apertado demais; n = 14 deixa margem.
              - LLC: ~metade da LLC que 1 thread vê (L3 da sua CCX no AMD, L2
                do seu CMG no A64FX), acima das caches privadas.
              - RAM: n = 500 cumpre > 1 GiB e evita potências de 2 (n = 512),
                que podem causar conflitos de cache (aliasing) e confundir a
                análise. Cabe nos ~8 GiB de 1 CMG do A64FX.
Alternativas: n = 512 na RAM (1.52 GiB): rejeitado pelo risco de aliasing.
Impacto:      Gerar com tools/gen_input.py varcoef --dims n n n. Confirmar os
              limites de L1/LLC com a curva de latência (D07). Se mudarmos as
              estruturas (ex.: material em uint8 -> 9 B/ponto), recalcular o
              tamanho ocupado pela NOSSA versão.
Estado:       DECIDIDO (Rodrigo, 20/11/2026); n RAM e LLC do nó revistos
              pela D22 (21/11/2026).

[D16] Tetos da 1.3 para o varcoef                        (20/11/2026, Task 1.3)
